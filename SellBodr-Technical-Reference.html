01

Problem Statement

Sellers looking to export Indian-manufactured products to global eCommerce marketplaces face a fragmented research process spread across dozens of tools, none of which answer the six decisive questions a seller must resolve before committing capital and effort to a product opportunity.

  • 1
    Which products have strong demand?
    Search volume trends, BSR rankings, seasonal patterns, review velocity
  • 2
    Which products have low competition?
    Active seller count, average listing quality, price compression, review depth
  • 3
    Which products have good margins?
    Sale price minus all costs including fees, ads, freight, and duties
  • 4
    Which marketplace and country is best?
    Amazon US/UK/DE/CA/AU, Etsy, eBay, Walmart, TikTok Shop — cross-compared
  • 5
    Is India sourcing feasible?
    Cost, MOQ, lead time, supplier trust score, category depth in India
  • 6
    What is the estimated net profit?
    After fees, shipping, packaging, import duty, ad spend, and taxes
Current Market Gap

Existing tools (Helium 10, Jungle Scout, Keepa) serve US-centric Amazon sellers. None are designed for an Indian exporter's perspective — sourcing in INR, shipping internationally, navigating Indian supplier ecosystems (IndiaMART, TradeIndia), and benchmarking across nine global marketplaces simultaneously. SellBodr fills that gap with a unified AI pipeline that answers all six questions in a single scan.

Every product opportunity passes through six sequential stages, each owned by one or more AI agents. Agents read and write to a shared data store, enriching the record at each stage before the final Recommendation is materialised.

Data Flow Principles

Each stage produces a typed JSON record persisted to the opportunities table in Turso. Downstream stages consume this record rather than re-fetching raw data. The AI agent pipeline is triggered by POST /api/opportunities/scan and streams live progress updates to the client through a 7-stage animated progress panel. Historical records are immutable — score changes require creating a new scan, not overwriting the old one, to maintain auditability and reproducibility via scoreVersion.

Authentication System

SellBodr uses WebAuthn (passkeys) as the primary and sole authentication factor — no passwords. Registration and login are handled by SimpleWebAuthn on both client and server. JWTs are signed with jose and stored in localStorage.

Registration Flow

Step 1: Plan selection (Free / Pro / Organisation)
Step 2: Name + email form
Step 3: Passkey enrollment via platform authenticator — Windows Hello, Touch ID, or hardware key
Step 4: credentialId + publicKey stored in passkey_credentials table
Step 5: JWT issued, stored as bs_access_token in localStorage

Login Flow

Step 1: Email entry — server looks up user and their credential IDs
Step 2: Browser prompts passkey assertion (biometric / PIN)
Step 3: Server verifies assertion against stored public key via SimpleWebAuthn
Step 4: Counter checked for replay protection; updated in DB
Step 5: JWT issued; user JSON stored as bs_user in localStorage

Passkey Error Handling

Accounts registered before passkey support was introduced, or where the authenticator credential has been lost, are handled gracefully. The login flow checks whether a passkey credential exists for the given email before initiating WebAuthn assertion. If no credential is found, the user is redirected to the registration page with a clear error message rather than surfacing a cryptic WebAuthn API error. Accounts can enroll additional passkeys from the Settings page once authenticated.

08

AI Agent Pipeline

Every product scan runs through a deterministic 7-stage pipeline. Each stage is an agent that consumes typed input from the shared opportunity record, enriches it, and writes structured JSON output. Agents never call models directly — all LLM calls are routed through the model gateway in packages/agents for logging, cost tracking, caching, and provider swapping.

1
Discovering — Keyword Expansion
Takes the user's raw search term and generates related product variants, sub-categories, and trending adjacent searches. Produces a canonical product taxonomy node and a list of expanded keywords that guide downstream agents. Output: { canonicalProduct, variants[], searchTerms[], categoryPath }
2
Demand — Market Signal Analysis
Analyses search volume trends, seasonal patterns, BSR (Best Seller Rank) movement, and review velocity across target marketplaces. Returns a demand signal score with source citations and confidence level. Output: { demandScore, searchVolume, trend, seasonality, bsrData[], reviewVelocity, confidence }
3
Competition — Seller Landscape
Counts active sellers, scores listing quality (title completeness, image count, review depth), maps price distribution, and identifies price floors and ceilings. Output: { sellerCount, avgReviews, priceRange, listingQualityScore, competitionScore, topCompetitors[] }
4
Suppliers — India Sourcing
Queries 10 supplier platform connectors (IndiaMART, TradeIndia, Alibaba, Moglix, IndiaBizForSale, ExportersIndia, JustDial, GlobalLinker, MSME India, Amazon India). Returns unit cost (paise), MOQ, lead time days, trust score, and qualityIndicators JSON (certifications, years active, review count). Output: SourcingCandidate[]
5
Profit — Full P&L Calculation
Computes net profit using: Sale Price − Source Cost − Shipping − Packaging − Import Duty − Marketplace Fees − Ad Spend = Net Profit. All monetary values in integer minor units. Applies marketplace-specific fee structures (Amazon FBA: 15% referral + FBA fulfilment; Etsy: 6.5% transaction + listing fee; etc.). Output: { salePrice, sourceCost, shippingCost, packagingCost, importDuty, marketplaceFee, adSpend, netProfit, netMarginPct }
6
Scoring — Opportunity Score Computation
Runs the 7 sub-score formulas from packages/core/scoring. Weights are applied and combined into the composite Opportunity Score (0–100). The scoreVersion field is stamped to ensure historical reproducibility. Output: { opportunityScore, subScores: { demand, competition, margin, saturation, trend, shipping, marketplaceFit }, scoreVersion }
7
Verdicts — Recommendation Generation
Applies threshold rules to produce a final Launch / Hold / Reject recommendation with a confidence percentage. Also generates the Launch Assets (title, bullets, description, backend keywords, PPC campaign structure) for Launch verdicts. Output: { recommendation, confidence, rationale, listingAssets?, ppcStructure? }

Opportunity Scoring

The Opportunity Score is the core intellectual property of SellBodr. It is a composite of seven sub-scores, each bounded 0–100. Formulas are defined once in packages/core/scoring and imported everywhere — never reimplemented inline. Every score carries a scoreVersion so historical recommendations remain reproducible even as the formula evolves.

7 Sub-Scores

1. Demand ScoreSearch volume · trend · seasonality · BSR velocity
2. Competition ScoreInverse of seller density · listing quality · review depth
3. Margin ScoreNet profit ÷ sale price · absolute dollar threshold
4. Market Saturation ScoreAvailable shelf space vs. active SKU count
5. Trend ScoreMomentum direction over 90/180-day window
6. Shipping Feasibility ScoreWeight + dimensions vs. freight cost viability
7. Marketplace Fit ScoreCategory alignment + policy compliance + seasonal fit

Composite Formula

// packages/core/scoring/opportunityScore.ts
export function computeOpportunityScore(subScores: SubScores): ScoredOpportunity {
  const weights = {
    demand:         0.25,
    competition:    0.20,
    margin:         0.20,
    saturation:     0.10,
    trend:          0.10,
    shipping:       0.08,
    marketplaceFit: 0.07,
  };

  const composite = Object.entries(weights).reduce((acc, [key, w]) => {
    return acc + subScores[key as keyof SubScores] * w;
  }, 0);

  return {
    opportunityScore: Math.round(composite),
    subScores,
    scoreVersion: SCORE_VERSION, // bumped on any formula change
  };
}

Frontend Architecture

The web application is a Next.js 14 App Router project with TypeScript strict mode. Server components handle data fetching and initial render; client components handle interactivity. Route groups separate auth pages from dashboard pages.

Route Groups

(auth) group

Contains /login and /register. No shared layout wrapper — each page is standalone with its own centered card layout. Auth state is absent here; if a JWT is already present, the page redirects to /opportunities.

(dash) group

All authenticated pages share layout.tsx which renders the top header navigation, mobile bottom tab bar, slide-in mobile drawer, PWAInstallBanner, and CurrencyWidget. The layout checks for bs_access_token in localStorage and redirects to /login if absent.

Key Library Files

lib/api.tsTyped API client. All fetch calls go through here. Reads bs_access_token from localStorage and attaches as Authorization: Bearer header. Throws typed ApiError on non-2xx responses.
lib/auth.tsJWT decode helpers, isPro(user), isAdmin(user), getUser() from localStorage. No server-side session — purely client-side JWT validation for UI gating (server always re-validates via JwtAuthGuard).
lib/db.tsTurso @libsql/client singleton. Reads TURSO_URL and TURSO_TOKEN from environment. Used only in API route handlers (server-side), never in client components.

API Layer

The API is implemented as Next.js Route Handlers (App Router app/api/ directory) following NestJS modular conventions. Guards are applied as middleware wrappers. All responses are typed JSON. No REST framework is used directly — the architecture is inspired by NestJS but runs natively in Next.js serverless functions on Vercel.

Authentication Endpoints

  • POST/api/auth/registerRegister new user account (plan, name, email)
  • POST/api/auth/loginEmail lookup before passkey flow begins
  • POST/api/auth/passkey/register-beginGenerate WebAuthn registration options (challenge)
  • POST/api/auth/passkey/register-completeVerify attestation, store credential, issue JWT
  • POST/api/auth/passkey/login-beginGenerate WebAuthn assertion options for user's credentials
  • POST/api/auth/passkey/login-completeVerify assertion, update counter, issue JWT

Opportunities Endpoints

  • POST/api/opportunities/scanTrigger 7-stage AI pipeline; streams progress via SSE; returns opportunity record
  • GET/api/opportunitiesList opportunities for auth user; supports filters: score, recommendation, marketplace, country
  • GET/api/opportunities/:idFull opportunity detail including all JSON sub-fields
  • POST/api/opportunities/:id/rescanRe-run pipeline on existing opportunity with latest data

Suppliers Endpoints

  • GET/api/suppliers/:idFull supplier profile with qualityIndicators and contactInfo
  • POST/api/suppliers/searchSearch for additional suppliers beyond initial pipeline results (Pro only)

Admin Endpoints

Guards & Middleware

JwtAuthGuard

Validates Authorization: Bearer <token> header. Verifies signature with jose using JWT_SECRET. Attaches decoded user to request context. Applied to all /api/(dash) routes.

EntitlementGuard

Checks user plan against required entitlement. For POST /api/opportunities/scan: enforces 5-scan lifetime limit for Free users, blocks if exceeded. Admin bypasses all entitlement checks.

AdminGuard

Applied to all /api/admin/* routes. Checks isAdmin(user). Returns 403 Forbidden for non-admin requests. Admin is either role='admin' in DB or hardcoded email sellbodr@gmail.com.

Engineering Conventions

These are hard rules for all contributors — human and AI alike. They exist to keep the codebase auditable, reproducible, and maintainable as the team scales.

  • TS
    TypeScript everywhere — no any without justification
    TypeScript strict mode is enforced. any is only permitted with an explicit // eslint-disable-next-line @typescript-eslint/no-explicit-any comment and a reason. tsc --noEmit must pass before every deploy. Zod schemas validate all external data at the boundary.
  • $
    Money is never a float
    All monetary values are stored and computed as integer minor units (paise for INR, cents for USD). A Money value object in packages/core/money always carries the currency code. Floating-point arithmetic is never used for financial calculations.
  • 📦
    Domain logic lives in packages/core
    UI (apps/web) and API (apps/api) are thin shells. All scoring formulas, type definitions, and business rules are defined once in packages/core and imported everywhere. Never reimplement a scoring formula inline.
  • 🤖
    Agents never call models directly
    All LLM invocations are routed through the model gateway in packages/agents. This enables unified logging, cost tracking, response caching, rate limiting, and provider swapping without touching agent logic.
  • 🔌
    External calls through packages/connectors
    No marketplace SDK or supplier platform client is imported directly in apps/. All external integrations are behind typed interfaces in packages/connectors. This allows mocking in tests and provider swapping without UI/API changes.
  • 📝
    Every write is auditable
    All mutations (create/update/delete on any entity) emit a domain event that is consumed by the audit log writer and persisted to audit_log. The audit log is append-only. This covers user management, subscription changes, opportunity creation, and admin actions.
  • 🚩
    Feature flags default off in production
    Every new surface is gated behind a feature flag. Flags default to false in production and are enabled explicitly per environment. This prevents incomplete features from reaching users and enables gradual rollout.
  • 🔁
    Idempotency on all job handlers
    BullMQ job handlers are keyed by a deterministic job ID derived from the input (e.g. SHA256(userId + keyword + marketplace)). Duplicate jobs are deduplicated at enqueue time. Handlers check for existing results before executing to avoid double-processing.
  • 📊
    Scoring changes require a version bump
    The SCORE_VERSION constant in packages/core/scoring is bumped on every formula change. All opportunity records store the scoreVersion at scan time. This ensures historical recommendations remain reproducible — you can always re-run the exact formula that produced a past score.

Glossary

Canonical definitions for all domain terms used in this document, the codebase, and communications. When in doubt about a term, refer here — the definition is the source of truth.

Opportunity
A specific (product × marketplace × country) candidate being evaluated by the AI pipeline. One user search may produce multiple opportunities across different marketplace + country combinations.
Opportunity Score
The composite 0–100 ranking of an Opportunity, computed from seven weighted sub-scores. The primary signal for the Launch/Hold/Reject recommendation. Tied to a scoreVersion.
Sourcing Candidate
A specific Indian supplier offer for a product — includes unit cost (in paise), MOQ, lead time days, feasibility rating, and a reference to the supplier record. Multiple sourcing candidates exist per opportunity.
Landed Cost
The total cost to get one unit of product to the destination fulfilment centre: product cost + packaging + international freight + import duties. This is the cost basis for margin calculation.
Net Margin
The percentage profit after all deductions: (Sale Price − Landed Cost − Marketplace Fees − Ad Spend − Tax) ÷ Sale Price × 100. The minimum threshold for a Launch verdict is 25%.
Launch Assets
AI-generated marketplace listing content: title (optimised for search + character limits), 5 bullet points, long-form product description, backend keyword set, and initial PPC campaign structure. Generated in Stage 7 of the pipeline for Launch verdicts.
ProGate
A React component that wraps any Pro-only feature. In full mode it renders a full-page upgrade overlay. In inline mode it renders a soft blur with an inline upgrade CTA. Passes through to children for Pro and Admin users.
scoreVersion
A semantic version string (e.g. 'v2.1') stamped on every opportunity record at scan time. Identifies the exact scoring formula used. Required for historical reproducibility — changing the formula without bumping this version is a breaking convention violation.
EntitlementGuard
A NestJS-style API guard applied to routes that require a specific plan. For Free users it enforces the 5 lifetime scan limit and 10 results per marketplace cap. Pro users and Admins bypass all entitlement checks.
qualityIndicators
A JSON field on the suppliers table containing per-platform quality signals — certifications (ISO, GST, MSME), years in business, review/rating count, export experience, sample availability. Structure varies by supplier platform.
BSR
Best Seller Rank — Amazon's category ranking metric. Lower BSR = higher sales velocity. Used as a demand signal in Stage 2 of the AI pipeline. BSR velocity (rate of change) is more informative than the absolute value.
Model Gateway
The abstraction layer in packages/agents that all AI agents must use to invoke LLMs. Handles provider routing (by plan), request logging, cost tracking, response caching, and retry logic. Never import an AI SDK directly in agent code.
